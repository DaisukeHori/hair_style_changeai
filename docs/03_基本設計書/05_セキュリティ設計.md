# 第5章 セキュリティ設計

## 5.1 セキュリティ方針

### 5.1.1 基本方針

| 方針 | 説明 |
|------|------|
| 多層防御 | 複数のセキュリティレイヤーで保護 |
| 最小権限 | 必要最小限の権限のみ付与 |
| デフォルト拒否 | 明示的に許可されない限りアクセス拒否 |
| データ保護 | 個人情報の暗号化・アクセス制御 |

### 5.2.2 JWT構造

```typescript
// JWT Payload

  "aud": "authenticated",
  "exp": 1705320000,  // 有効期限
  "sub": "user-uuid", // ユーザーID

  "role": "authenticated",

  }

```

### 5.2.3 パスワードポリシー

| 項目 | 要件 |
|------|------|
| 最小長 | 8文字以上 |
| 複雑性 | 英数字混合必須 |
| 履歴 | 過去3回と同一不可 |
| 有効期限 | 90日（推奨） |
| ロック条件 | 5回連続失敗で10分ロック |

### 5.2.4 セッション管理

| 項目 | 設定値 |
|------|--------|
| Access Token有効期限 | 1時間 |
| Refresh Token有効期限 | 7日間 |
| アイドルタイムアウト | 30分 |
| 同時セッション | 3デバイスまで |

## 5.3 認可設計

### 5.3.1 ロール定義

```
ロール階層
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

owner (オーナー)
├── 全権限
├── スタッフ管理（追加/削除/権限変更）
├── 店舗設定変更
└── 売上・分析データ閲覧

manager (マネージャー)
├── スタッフ管理（追加/編集）
├── 全顧客データ閲覧/編集
├── 売上データ閲覧
└── 予約管理（全スタッフ分）

stylist (スタイリスト)
├── 担当顧客データ閲覧/編集
├── 施術記録作成
├── 自分の予約管理
└── スタイル提案

assistant (アシスタント)
├── 顧客データ閲覧（制限付き）
├── 施術補助記録
└── 予約閲覧
```

### 5.3.2 権限マトリクス

| 機能 | owner | manager | stylist | assistant |
|------|:-----:|:-------:|:-------:|:---------:|
| スタッフ追加 | ○ | ○ | - | - |
| スタッフ削除 | ○ | - | - | - |
| 顧客登録 | ○ | ○ | ○ | - |
| 顧客編集 | ○ | ○ | ○ | - |
| 顧客削除 | ○ | ○ | - | - |
| 施術記録作成 | ○ | ○ | ○ | △ |
| 売上閲覧 | ○ | ○ | △ | - |
| 店舗設定変更 | ○ | - | - | - |

### 5.3.3 Row Level Security

```sql
-- RLSポリシー例: customers テーブル

-- 同一店舗のデータのみ閲覧可能
CREATE POLICY "salon_isolation_select" ON customers
FOR SELECT USING (
    salon_id = (
        SELECT salon_id FROM stylists
        WHERE auth_user_id = auth.uid()
    )
);

-- スタイリスト以上は登録可能
CREATE POLICY "stylist_can_insert" ON customers
FOR INSERT WITH CHECK (
    salon_id = (
        SELECT salon_id FROM stylists
        WHERE auth_user_id = auth.uid()
        AND role IN ('owner', 'manager', 'stylist')
    )
);

-- マネージャー以上のみ削除可能
CREATE POLICY "manager_can_delete" ON customers
FOR DELETE USING (
    salon_id = (
        SELECT salon_id FROM stylists
        WHERE auth_user_id = auth.uid()
        AND role IN ('owner', 'manager')
    )
);
```

## 5.4 データ保護

### 5.4.1 暗号化

| 対象 | 暗号化方式 | 管理 |
|------|-----------|------|
| 通信 | TLS 1.3 | 自動 |
| DB保存データ | AES-256 | Supabase管理 |
| バックアップ | AES-256 | Supabase管理 |
| 画像ファイル | 署名付きURL | アプリケーション |

### 5.4.2 機密データ取り扱い

```
機密データ分類
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【高機密】
├── パスワード（ハッシュ化して保存）
├── クレジットカード情報（取り扱わない）
└── APIキー（環境変数で管理）

【機密】
├── 顧客の個人情報（氏名、電話、メール）
├── 顧客の顔写真
├── アレルギー情報
└── 施術履歴

【一般】
├── スタイル画像
├── 店舗情報（公開）
└── システムログ
```

## 5.6 脆弱性対策

### 5.6.1 OWASP Top 10対策

| 脆弱性 | 対策 |
|--------|------|
| インジェクション | パラメータバインディング、ORM使用 |
| 認証の欠陥 | Supabase Auth、JWT |
| 機微データ露出 | TLS、暗号化、署名付きURL |
| XXE | XMLパーサー使用せず |
| アクセス制御の欠陥 | RLS、RBAC |
| 設定ミス | セキュアデフォルト、環境変数 |
| XSS | React自動エスケープ、CSP |
| 安全でないデシリアライズ | JSON使用 |
| 既知の脆弱性 | 依存関係の定期更新 |
| ログ・監視不足 | 監査ログ、Sentry |

### 5.6.2 入力バリデーション
